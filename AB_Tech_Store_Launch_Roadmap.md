## 4. Implementation order (recommended)

Reasoning: ship trust-safety first (deploy identity, CPU guardrail, database safety), then make the catalogue true, then complete the storefront, then admin, then checkout hardening, then content/legal, then a full launch rehearsal. Filters come **after** the data is real, because filtering over placeholder products produces a polished façade around nothing.

```
Phase 0  Reliability + safety guardrails        (ops, no deploy)      ~0.5 day
Phase 1  Release hygiene: live == source        (commit + deploy)     ~0.5 day
Phase 2  Verify/complete migrations & DB safety (migration approval)  ~0.5 day
Phase 3  Catalogue truth + taxonomy + imagery   (data + code)         ~3–5 days
Phase 4  Storefront completion + filters + design                      4–6 days
Phase 5  Checkout/order hardening + email                              2–3 days
Phase 6  Trust content + contact + legal                              1–2 days
Phase 7  Admin completion (incl. homepage CMS decision)               2–4 days
Phase 8  Launch rehearsal + full checklist                            1–2 days
```

Phases 3–7 can partly run in parallel once Phase 2 is settled, but **Phase 1 must precede any deploy** and **Phase 0 should precede customer traffic**.

### Phase 2 — Database: verify what is applied, then migrate deliberately
**Production approval: yes** (migrations are explicitly out of scope until approved).

**Files:** `supabase/migrations/0002_admin_erp.sql`, `0003_suppliers.sql`, `0004_products_brand.sql`, `0005_email_center.sql`, `0006_customer_order_user_id.sql`, `0007_categories_taxonomy.sql`, `supabase/seed.sql`, `lib/server/catalog.ts`, `lib/site-config.ts`.

**Current state:** `schemas.md` records 0001 as applied and the storefront works against it. `lib/server/catalog.ts` states in-code that `categories.is_active` is **not** in the production schema, which means **0007 is not applied** (it is the only migration that adds that column, and it is idempotency-guarded). 0002–0006 are **unverified**.

**Read-only verification the owner should run in the Supabase SQL editor** (no writes):

```sql
select table_name from information_schema.tables
 where table_schema = 'public' order by 1;

select column_name from information_schema.columns
 where table_schema = 'public' and table_name = 'categories' order by 1;

select column_name from information_schema.columns
 where table_schema = 'public' and table_name = 'products'
   and column_name in ('brand_id','is_active','is_featured');
```

Expected markers: 0002 → `brands`, `admin_roles`, `orders.notes`…; 0004 → `products.brand_id` and `product_images` kind `gallery`; 0005 → `email_events`, `followup_rules`; 0006 → `create_order(..., p_user_id)`; 0007 → `categories.is_active` + 14 active categories.

**Changes**
1. Apply only the migrations that are actually missing, one at a time, with the verification query after each.
2. Apply 0007 last: it rewrites the category taxonomy (relabels 3 rows, deactivates `tablets` + `audio`, inserts 11 categories, moves 5 products) and refuses to run against an unexpected state. It has a tested rollback.
3. After 0007, restore `.eq("is_active", true)` on the categories query in `lib/server/catalog.ts` (there is a `TODO(0007)` marking the exact spot).

**Risks:** 0007 mutates live category rows; a partially applied migration is refused by design, but a mid-run failure would leave the transaction rolled back (it is wrapped in `BEGIN/COMMIT`). 0006 changes the `create_order` signature — do **not** enable `ORDER_OWNERSHIP_ENABLED` in the same release.

**Tests:** verification SQL after each migration; `/shop` still renders; product counts unchanged (the migration asserts 12); category labels match the taxonomy; order creation still succeeds with five arguments.

### Phase 4 — Storefront completion: filters, design, responsive polish
**Production approval: yes** (deploy). No schema change if Phase 3.2 landed.

**Files:** `app/shop/page.tsx`, `components/ShopControls.tsx`, `lib/products.ts` (filter/sort helpers), `lib/server/catalog.ts`, `app/globals.css`, `components/ProductCard.tsx`, `components/ProductDetail.tsx`, `components/HomeView.tsx`, `components/CategoryPanel.tsx`, `components/Footer.tsx`.

**Changes**
1. **Filter model — URL-driven, server-computed, no extra queries.** Extend `app/shop/page.tsx` `searchParams` with:
   `brand` (repeatable), `min`/`max` (price), `stock=in`, `rating` (≥4), `colour` (repeatable), and spec facets `spec.<key>=<value>` (e.g. `spec.RAM=16GB`). All filtering runs on the single catalogue already loaded per request, so CPU does not grow with filter count.
2. **Facet source.** Brand from `products.brand_id`. Colour from `product_variants.options->>'colour'` (the `options` jsonb already exists in 0001 — **no migration needed**). Technical facets derived from the existing `specs` jsonb: collect distinct spec keys per category and render only the ones present. Add a normalised facet table only if the derived approach measurably slows rendering.
3. **Filter UI**: a left rail on desktop (`components/ShopControls.tsx` gains a facet panel), a bottom-sheet/drawer on mobile, chips for active filters, "clear all", result count, and stable ordering. Keep every filter in the URL so results are shareable and back/forward works.
4. **Search**: keep `searchProducts` for instant client behaviour, but make the server path search the same fields consistently. Add pagination at ~24/page the moment the catalogue exceeds a page.
5. **Design pass** (premium, not generic): establish a token set in `app/globals.css` (currently 7 custom properties across 1,295 lines) covering type scale, spacing, radius, elevation, colour and motion; apply consistently to cards, headings, buttons, forms and the hero. Remove the reference theme's visual fingerprints rather than copying them.
6. **Mobile**: `.category-row` and `.shop-cats` already scroll horizontally with snap — keep that, verify at 360/390/430 px. Ensure the desktop `CategoryPanel` rail stays desktop-only and that the mobile menu covers the full 14-category list.

**Risks:** URL param sprawl (validate and ignore unknown values); filter state bugs on back/forward; a heavy filter rail on mid-size screens; regressions in sort + search interaction.

**Tests:** each filter alone and combined; invalid params ignored; counts match; back/forward restores state; 360 px and 1,440 px screenshots reviewed; keyboard-only filter operation; no layout shift on the product grid.

### Phase 5 — Checkout and order hardening
**Production approval: yes** (deploy; email requires a secret set by the owner).

**Files:** `lib/server/orders.ts`, `app/api/orders/route.ts`, `components/CheckoutView.tsx`, `app/order/[ref]/page.tsx`, `lib/server/email.ts`, `lib/server/email-config.ts`, `app/api/admin/orders/[id]/email/route.ts`.

**Changes**
1. **Unknown-outcome handling (from the evidence report, R3).** Distinguish: *definitely not saved* (validation `400`, business rule `409`, pre-send failure) → "not placed, try again"; *definitely saved* (RPC returned a ref) → confirmation; *unknown* (abort/timeout after send) → "we may have received your order", point at `/order/<ref>`/support, never invite a blind retry. No schema change needed for the messaging; an idempotency key would need one and is optional.
2. **Order confirmation email.** Requires `RESEND_API_KEY` + `RESEND_FROM_EMAIL` as Worker secrets (owner sets them; never in chat or repo). `lib/server/email.ts` already degrades gracefully when unset. Until it is set, the order page must not promise an email.
3. **Stock integrity**: verify `create_order` still re-prices and decrements atomically after any 0006 change; add a low-stock admin signal.
4. **Checkout UX**: inline validation, fee breakdown from `store_settings`, express/standard clarity, and an explicit "no payment taken online" note while payment is merchant-offline.

**Risks:** changing failure copy without correct classification could tell a customer their order failed when it succeeded (the current bug) — or the inverse. Test both directions. Email sending must never block a successful order (already structured that way; keep it).

**Tests:** simulated timeout after send → "unknown" copy, no duplicate row; validation errors → 400 with field messages; successful order → `/order/<ref>` loads and appears in admin; email unset → order still completes; email set → one email, no retry storm.
